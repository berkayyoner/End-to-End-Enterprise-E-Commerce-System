1.1: Built auth-service's user domain and wired it to a real Spring Authorization Server per OAUTH2.md - AppUser entity (email/password hash/name/phone/idVerified/seller, extends common-lib's BaseEntity) with a validated POST /register endpoint; a second, HIGHEST_PRECEDENCE-ordered SecurityFilterChain scoped via `.securityMatcher(authorizationServerConfigurer.getEndpointsMatcher())` hosts the AS endpoints (registeredClientRepository with the berkay-public-client PKCE public client, AuthorizationServerSettings using the gateway-facing issuer per OAUTH2.md §4, a freshly-generated RSA JWKSource/JwtDecoder, and an OAuth2TokenCustomizer adding account_type/id_verified claims), while a lower-priority default chain handles form login at POST /login (JSON success/failure responses, since the SPA calls it via fetch, not a browser navigation) with cookie-based CSRF and a /csrf-token bootstrap endpoint. Verified the entire flow live against the real Oracle instance: register -> fetch CSRF token -> login (200 JSON) -> GET /oauth2/authorize with PKCE using the authenticated session (302 with a code, no consent screen) -> POST /oauth2/token -> got back a correctly-signed JWT with the right iss/aud/account_type/id_verified claims. Also discovered and documented in OAUTH2.md (via bytecode inspection of OAuth2RefreshTokenGenerator, since no docs were available for this snapshot version) that Spring Authorization Server deliberately never issues refresh tokens to public/no-secret clients - the SPA renews its 15-minute access token via a silent /oauth2/authorize replay against the existing session instead, which is the current OAuth 2.1-aligned recommended pattern rather than a compromise.
1.2: Added auth-service's personnel domain, kept entirely separate from public AppUser per RULES.md - PermissionGroup/PermissionEntry entities implementing the P0-P5 + A/E/D evaluation logic (hasView/hasAdd/hasEdit/hasDelete, toCodes() rendering exactly like RULES.md's "P0AED"/"P2ED"/"P3"/"P4A" examples, covered by 5 passing unit tests) and a Personnel entity (one PermissionGroup per personnel, never none). Hit and fixed a real LazyInitializationException (personnel.getPermissionGroup() accessed outside a transaction in both the UserDetailsService and the token customizer) by adding a join-fetch repository query instead of relying on transaction scoping. Verified live end-to-end against Oracle: fresh boot bootstraps the admin account, personnel login succeeds (200 JSON), and the full PKCE authorization_code exchange for berkay-personnel-client returns a JWT with the correct account_type=PERSONNEL and permissions=["P0AED"] claims.
1.3: Added the P0-only "Permissions" management API on auth-service - PermissionGroup CRUD (GET list/get, POST create, PUT update, DELETE soft-delete) under /personnel/permission-groups, each verb requiring the matching decomposed authority (PermissionGroup#toAuthorities: PERM_P0_VIEW/_ADD/_EDIT/_DELETE) via @PreAuthorize + @EnableMethodSecurity, enforced against the same session established by task 1.2's personnel login (no separate resource-server JWT validation needed since the caller is already in-session on the same server). Hit and fixed two real bugs found only by testing against the live Oracle instance: (1) re-granting an unchanged page code during update did remove+insert instead of updating in place, which Hibernate's insert-before-delete flush ordering turned into a transient unique-constraint violation - fixed by updating the existing PermissionEntry row's flags instead of replacing it; (2) the DB-level unique constraint on permission_group.name blocked reusing a name after its group was soft-deleted, contradicting the app-level existsByNameAndDeletedFalse check - removed the raw column constraint in favor of app-layer-only uniqueness (a bare unique index can't express "unique among non-deleted rows" without a function-based index, not worth the machinery before a migration tool exists), and reset the affected local dev tables so the fix could be verified cleanly. Verified live end-to-end: create/update/delete/name-reuse-after-delete all behave correctly, and a seeded view-only personnel account gets 200 on GET but a clean 403 JSON on POST.
