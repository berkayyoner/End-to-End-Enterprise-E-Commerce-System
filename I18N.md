# Multi-Language (i18n) Strategy

Reference document for tasks **0.5** (backend) and **0.6** (frontend) in `ANALYSIS.md`. Default
language is Turkish (`tr`) per `RULES.md`; every layer must let a new language be added without
code changes.

## Backend (task 0.5)

### Translation table pattern

Any entity with seller/admin-editable text in multiple languages (Product, Category, Campaign, ...)
gets a companion `<entity>_translation` table instead of translatable columns on the entity itself:

```
product              (id, price, stock, ...)                          -- non-translatable data
product_translation  (id, product_id FK, locale_code, name, description, ...)
                     UNIQUE (product_id, locale_code)
```

Concrete translation entities extend `common-lib`'s `com.berkay.common.i18n.TranslationEntity`
(itself a `BaseEntity`, so it already carries id/audit/soft-delete columns) and add only:
* a `@ManyToOne` back to the owning entity (e.g. `product_id`)
* the translatable columns for that entity (e.g. `name`, `description`)
* a unique constraint on `(owning_id, locale_code)`

`locale_code` is a plain string (ISO 639-1, e.g. `tr`, `en`) - there is no enum of supported
codes anywhere in the code. Adding a language is inserting rows with a new `locale_code`; it
never requires a migration to code.

### Default locale & fallback

`com.berkay.common.i18n.LocaleCodes.DEFAULT_LOCALE = "tr"` is the single source of truth for the
platform default. Resolving which translation to show for a request uses
`com.berkay.common.i18n.TranslationResolver.resolve(translations, requestedLocale)`:

1. exact match on the requested locale,
2. else the default locale (`tr`),
3. else whatever translation exists (never render a blank name/description),
4. `Optional.empty()` only when the entity truly has zero translation rows (a data bug, not
   handled by inventing text).

This mirrors the frontend fallback in `example-bases/utils/translate.js` (requested → default →
key itself) so both layers fail the same way.

### Per-service ownership of reference/lookup data

All services share one physical Oracle schema/user (`berkay`, per `RULES.md` and
`CONVENTIONS.md`). Business tables stay single-owner per `CONVENTIONS.md` section 3, but a
`language` reference table (code, native name, is_default, is_active - for admin-panel "add a
language" UI in a later phase) is small, rarely-written lookup data: each service that needs it
(`product-service` for catalog translations now; others later) owns and seeds its own copy rather
than calling another service for a lookup on every request. This is a deliberate, documented
exception to the single-writer rule for static reference data only - it never applies to
transactional/business tables.

### What ships now vs. later

Task 0.5 delivers the reusable pattern (`TranslationEntity`, `TranslationResolver`,
`LocaleCodes`) in `common-lib`, covered by `TranslationResolverTest`. The concrete
`product_translation` / `category_translation` tables and the `language` reference table are
built when the owning entities are (`ANALYSIS.md` tasks 2.1 and 3.1), by extending
`TranslationEntity` - no further backend i18n groundwork is needed before then.

## Frontend (task 0.6)

Covered when task 0.6 is implemented: adapts `example-bases/hooks/useLanguage.js` and
`example-bases/utils/translate.js` into a shared i18n module for `berkay-public` and
`berkay-personnel`, with `tr` as the default/fallback language (the example base defaults to
`en` - this must be flipped to `tr` per `RULES.md`).
